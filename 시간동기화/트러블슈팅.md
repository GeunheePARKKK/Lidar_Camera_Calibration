**교훈 네 가지**

- **배선은 라이다 전원을 내리고 한다.** 켜진 채로 GPS 입력선을 물리면 입력을 인식 못 한 채 남는다 (2번).
- **GND부터 의심한다.** 이번 작업에서 GND·전원 레일 접촉 문제가 네 번 나왔다 (10, 11, 13번). 브레드보드 레일은 가운데서 끊겨 있는 경우가 많다.
- **모듈 핀 표기를 믿지 말고 정지 레벨 시험을 한다.** 입력을 GND ↔ 3V3로 손으로 바꿔 가며 출력이 따라오는지 보면 핀 방향이 바로 드러난다 (14번).
- **숫자가 이상하면 검사기부터 의심한다.** 유실 245개, GPRMC 불일치 209회 모두 데이터가 아니라 검사 로직의 문제였다 (5, 16번).

## 1. GPIO 직결로는 PPS `Absent`

- **증상** ESP32 GPIO5를 점퍼선 하나로 I/F박스 GPS PULSE에 연결. ESP32 로그상 PPS는 정확히 1,000,000 µs 간격으로 나가는데 라이다는 `pps_state = Absent`.
- **원인** 3.3 V GPIO로는 박스 입력을 구동하기 부족한 것으로 판단. 원래 배선 문서에도 PPS 경로에 "버퍼"가 명시되어 있었음.
- **해결** 74AHCT125 비반전 버퍼로 3.3 V → 5 V. 74HC가 아니라 **74HCT/AHCT**여야 함 (5 V 구동 시 74HC는 입력 HIGH 문턱이 3.5 V라 3.3 V를 못 넘김).

## 2. 버퍼를 넣어도 `Absent` → 라이다 전원 재투입

- **증상** 버퍼 출력은 정상인데 계속 `Absent`.
- **원인** 라이다가 **켜진 상태에서** PPS 선을 물림. 입력단이 신호를 인식하지 못하는 상태로 남음.
- **어떻게 찾았나** 사용자가 "켜진 채로 배선해서 그럴 수도 있다"며 전원을 껐다 켜자 즉시 `Locked`. 이후 풀업 저항을 바꿀 때 같은 증상이 재현되어 확정.
- **해결** GPS 입력 쪽 배선을 바꿀 때는 라이다 전원을 먼저 내리고, 배선 후 켠다.

## 3. Phase Lock offset 단위

- **증상** 없음 (발견해서 막음). 도 단위로 보냈다면 되읽기 확인까지 통과하면서 위상만 엉뚱한 곳에 맞았을 것.
- **원인** VLP-16 웹 UI(`tab/config.html`)가 `offset.value = 100 * offsetInput.value`로 보냄. 장비는 0.01° 단위.
- **해결** `lidar_config.py --offset`은 도 단위로 받아 × 100 해서 전송.

## 4. 유실 0인데 "수신 구멍 7곳"

- **원인** 패킷 유실을 호스트 도착 시각 간격으로 셈. 리눅스가 수신 스레드를 늦게 깨우면 패킷은 다 왔는데 도착 시각에 몇 ms 구멍이 생김.
- **해결** 라이다가 패킷에 직접 찍은 타임스탬프 간격(1,327.104 µs)으로 셈.

## 5. 유실 0인 세션을 "245개 유실"

- **원인** 패킷 시각을 `packet_ts_us[::384]`로 뽑았는데, 이 배열은 **거리 0인 점을 걸러낸 뒤**라 384 간격이 패킷 경계와 안 맞음. 무반사 점이 많은 장면일수록 어긋남이 커짐. 이전 세션들에서 0이 나온 건 우연.
- **해결** `vlp16.decode()`가 필터링 전에 패킷 단위 시각(`pkt_ts_us`, `pkt_host_ts`)을 따로 보관.

## 6 · 7. 검산기 폴더 탐색, 시리얼 포트 자동 선택

- 6: 카메라 3번만 꽂혀 `cam3/`에 저장된 세션을 cam1부터 찾아서 "프레임 없음". → 실제 `camN` 폴더 이름으로 탐색.
- 7: ESP32가 빠져 있으면 `collect.find_port`가 메인보드 `/dev/ttyS31`을 잡고 권한 오류처럼 죽음. → USB로 붙은 장치(VID 있음)만 인정.

## 8. 전원 재투입 후 Phase Lock이 `Off`

- **원인** `/cgi/setting/*`로 바꾼 값은 RAM에만 들어감. 웹 UI의 **Save Configuration**(`POST /cgi/save`)을 따로 해야 플래시에 남음.
- **해결** `lidar_config.py --save`. I/F박스 전원을 껐다 켠 뒤에도 `On`으로 유지되는 것을 확인.

## 9. ESP32가 CP2102로 잡힘

- **증상** `10c4:ea60 CP2102 → /dev/ttyUSB0`. 부트 메시지만 나오고 펌웨어 로그가 없음. 포트를 열 때마다 ESP32가 리셋됨.
- **원인** 개발보드의 USB-C 두 개 중 `UART` 쪽에 꽂음. 펌웨어는 `USB CDC On Boot: Enabled`라 로그가 네이티브 USB로만 나감. UART 포트는 DTR/RTS 자동 리셋 회로가 있어 열 때 리셋됨.
- **해결** `USB`라고 적힌 포트로 → `303a:1001 → /dev/ttyACM0`. 이 포트는 열어도 리셋되지 않음.

## 10. PPS와 NMEA가 동시에 없음 → I/F박스 GND

- **단서** 두 신호는 칩도 전원도 다른데 동시에 죽음 → 공통 부분(GND, 커넥터)을 의심.
- **해결** 사용자가 I/F박스 GND ↔ ESP32 GND 도통 검사 → 끊겨 있었음. 연결.

## 11. 74AHCT125 3번이 2.4 V 고정

- 5 V 레일 접촉 불량. 다시 꽂아 해결. 출력이 하이임피던스이거나 입력이 떠 있으면 중간 전압에 머묾.

## 12. ESP32가 시리얼이 막히면 PPS를 내리지 못함

**이번 작업에서 가장 중요한 발견입니다.**

- **증상** 74AHCT125 2번 핀이 3.3 V, 3번 핀이 5 V로 **고정**. 라이다 PPS `Absent`. ESP32 통계에 `GPRMC 전송 22 건 … 전송 누락 1755 건`.
- **원인** 펌웨어는 PPS를 **타이머 인터럽트에서 올리고**, 20 ms 뒤에 **`loop()`에서 내립니다.** PC에서 아무도 USB 시리얼을 읽지 않으면 출력 버퍼가 차서 `Serial.print`가 막히고, 그동안 `loop()`가 멈춰 PPS가 HIGH에서 내려오지 못합니다. GPRMC 송신도 `loop()`에서 하므로 같이 멈춥니다.
- **어떻게 찾았나** 같은 배선에서 시리얼만 읽어 주며 비교.

  | | 라이다 PPS |
  |---|---|
  | 시리얼을 안 읽을 때 | `Absent` 1,093 / 1,093 |
  | 계속 읽어 줄 때 | 2.3초 만에 `Locked` |

- **해결 (현재)** `record.py`가 카메라 모드든 라이다 단독 모드든 ESP32 시리얼을 항상 읽고, 세션마다 `mcu_log.txt`로 저장. MCU 연결 직후 PPS 재잠금을 기다린 뒤 녹화 시작.
- **해결 (예정)** 펌웨어 `setup()`에 `Serial.setTxTimeoutMs(0);` — USB 출력이 막혀도 기다리지 않고 버리게 해서 PC와 무관하게 PPS가 나가도록.
- **남은 의문** 09-09에는 같은 펌웨어로 시리얼을 안 읽어도 PPS가 유지됐습니다. 카메라가 빠져 로그량이 늘었다고 추정했지만, 카메라 1대를 붙여도 증상이 같아서 확인되지 않았습니다.

## 13. MAX3232 모듈의 이상한 측정값 → 모듈 GND 미연결

- **증상** RS-232 포트 2번이 0.3 V, 모듈 VCC를 빼면 1.4 V, 모듈 VCC ↔ GND가 0.8 V(3V3) / 1.2 V(5V). 박스 쪽 선을 뽑으면 모듈 VCC ↔ GND가 0 V.
- **원인** **모듈 GND가 아예 연결되지 않았음.** 모듈이 처음부터 꺼져 있었고, 위 값들은 GPS RECEIVE 선이나 RXD 핀을 통해 새어 들어온 전압이었음.
- **해결** 모듈 GND를 ESP32 GND에 직접 연결 → **모듈 전원 LED가 처음으로 켜짐.**
- 모듈이 꺼진 상태에서 한 RXD/TXD·포트 2/3번 시험은 전부 무효였음.

## 14. 모듈 입력은 RXD가 아니라 TXD

- **증상** 모듈을 켠 뒤, RXD를 GND로 내려도 RS-232 포트 2번이 −5 V 그대로.
- **어떻게 찾았나** 정지 레벨 시험 — 입력 핀을 손으로 ESP32 GND / 3V3에 꽂아 가며 출력을 잼.

  | TXD에 꽂은 것 | RS-232 포트 2번 |
  |---|---|
  | ESP32 GND | **+6 V** |
  | ESP32 3V3 | **−5 V** |

- **해결** ESP32 GPIO17 → 모듈 **TXD**. 모듈 **RXD는 비움** — 이 모듈에서 RXD는 출력이라 VCC 5 V일 때 5 V가 나오므로 ESP32에 물리면 안 됨.
- 이런 모듈은 TTL 쪽 핀 이름을 "MCU의 어느 핀에 꽂으라"는 뜻으로 적는 제품과 "모듈 자신의 핀"으로 적는 제품이 섞여 있음.

## 15. GPRMC가 깨져서 들어옴

- **증상** 모듈 VCC 3.3 V, 입력은 RXD(잘못된 핀)일 때 라이다가 `$GPRMC�b3552.2������r…`를 받음. `$GPRMC`, `3552.2` 같은 조각만 맞음. 속도나 극성이 틀렸다면 전부 깨져야 하므로 비트 단위로 틀리는 증상.
- **원인** 진짜 입력(TXD)이 비어 있는 상태에서 옆 핀 신호를 조금씩 주워 담아 흘려보냄. 출력도 −3.3 V로 RS-232 경계선(−3 V)에 걸려 있었음.
- **해결** VCC 5 V + 입력 TXD → **깨진 문장 0, 체크섬 정상 문장만 수신.** (VCC 3.3 V + TXD 조합은 시험하지 않음)

## 16. GPRMC 대조 "+1초 209회"

- **원인** 위치 패킷의 NMEA 칸에는 마지막으로 받은 문장이 남아 있음. 매초 PPS 직후 새 문장이 도착하기 전(9600 bps로 66글자 ≈ 69 ms) 동안은 직전 초의 문장이라 +1로 보임.

  | 라이다 초 − 문장 초 | 초 경계 이후 |
  |---|---|
  | 0 (2,706회) | 70.9 ~ 999.8 ms |
  | +1 (209회) | 0.0 ~ 70.0 ms |

- **해결** 정상. `sync_report.py`가 이 구간을 알고 판정하도록 수정.

## 17. `READY 를 받지 못했습니다`

- **원인** 포트를 여는 순간 호스트 tty가 ESP32 출력을 되돌려 보내(echo) ESP32 명령 버퍼에 로그 조각이 섞임. 그 뒤에 붙은 `PING`이 알 수 없는 명령이 됨. ESP32 통계에 `알 수 없는 명령 : # ===== 방식`이 찍힌 것이 흔적.
- **해결** `record.py`가 개행으로 버퍼를 비우고 `PING`을 한 번 더 보냄.

## 18. Line1 노출 신호가 ESP32에 안 들어옴 (미해결)

- **증상** `CNT,201,0,359,0,0` (카메라 S/N …139), `CNT,200,0,396,0,0` (S/N …137). 연결한 카메라의 채널은 0이고, 채널 2(GPIO15)만 트리거의 약 2배를 셈.
- **처음 추정 (틀림)** "하나만 연결할 때 늘 같은 커넥터에 꽂고, 그 커넥터가 GPIO15로 간다."
- **실제** ESP32가 기록한 채널 2의 엣지 시각(session_017, 노출 8 ms)을 보면:

  | 트리거 | 첫 엣지 (트리거 후) | 둘째 엣지 | 둘 사이 |
  |---|---|---|---|
  | 1 | 8,058 µs | 58,062 µs | 50,004 µs |
  | 2 | 8,093 µs | 58,104 µs | 50,011 µs |
  | 3 | 8,115 µs | 58,144 µs | 50,029 µs |
  | 4 | 8,171 µs | 58,203 µs | 50,032 µs |

  카메라 노출이라면 지연이 매번 같아야 하는데 계속 밀리고, 둘째 엣지는 **펌웨어 락아웃(`EXP_LOCKOUT_US` = 50 ms)이 풀리자마자** 찍힘. 즉 채널 2 입력은 쉬지 않고 튀는 잡음이고, 락아웃이 샘플링만 하고 있음. 카운트가 트리거의 약 2배인 것도 100 ms ÷ 50 ms 그대로.
- **결론** 카메라의 Line1(ExposureActive) 신호는 ESP32 어느 채널에도 들어오지 않고 있음. GPIO15는 떠 있거나 잡음을 받는 상태.
- **영향** 촬영과 동기에는 영향 없음. 다만 **카메라 트리거 → 실제 노출 시작 지연**을 µs 단위로 잴 수단과, 트리거를 놓쳤는지 검출하는 기능이 막혀 있음.
- **확인할 것** 연결된 카메라의 HR25 Pin8(주황, Line1+) → 해당 GPIO와 4.7 kΩ 풀업(3.3 V), Pin7(초록, Line1−) → GND 배선. 펌웨어 `L` 명령으로 각 핀의 대기 레벨이 HIGH인지. 쓰지 않는 Line1 입력은 풀업이나 GND로 고정.
